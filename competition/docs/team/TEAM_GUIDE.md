团队目标是 **2026-10-31 交付可验收版本，10-28 起冻结新功能**。这是内部目标，不替代官方报名、材料或比赛日期。当前离线准备；用户到场后先用已正常工作的手柄采有用路段，随后回放。新程序自主运动单独安排，真实设备统一由甲/A 接入。

## 要完成的比赛任务

工作路线为出库后沿 1→2→3→4→5→6→7→8 完成两圈，覆盖三个锥桶交错绕行、每圈逆时针环岛一整圈、S 弯、人行道前实测停稳至少 3 秒并提示、横杆落下时持续等待，最后第二圈倒车入库并停住。第一圈经过车库应继续，不能误入库。

逆时针来自团队已确认方向。正式规则、补充通知、桶的经过侧别、轮胎边界和入库终点需乙现场核对；D 的合成场景采用的侧别/拓扑不是实测路线。没有检测到横杆不等于可以通行，满 3 秒也不等于可以开走。需要接管或搬车就保留事件，不能称该次自主完成。

## 三个人每天各交什么

| 人员 | 固定职责 | 对接 AI | 当天产物 |
|---|---|---|---|
| 甲：集成与底盘 | 代码版本、相机/反馈映射、部署、依赖、未来标定与唯一速度输出 | A | 已验收版本、运行/停止/回退方法、日志、待解决接口 |
| 乙：赛道与数据 | 规则和尺寸、道具位置、采集用途、之后的手柄示范、事件、标注和质量 | B | 会话目录与质量报告、场景清单、失败/纠正区间、数据共享清单 |
| 丙：感知与任务 | 帧回放、道路与目标识别、任务证据、判断是否需要训练 | C、D 分时 | 叠加图、失败例、任务回放结果、下一次补采需求 |

相机检查时：甲管终端，乙确认高低相机对应，丙核对视野与记录结果。未来恢复运动窗口后，同一轮明确谁启动/停车、谁驾驶或观察轮胎、谁拍全场录像；自主验收中手柄介入必须记作接管。

每天交接四句话：验收了什么、证据在哪里、什么仍失败、下一项做什么。记录代码版本、配置、会话编号和主要改变，不仅写“运行正常”。

## 现有四个 AI 实际交付

| 模块 | 仓库已有能力 | 当前仍缺什么 |
|---|---|---|
| A 总控/底盘 | 工程基线、公共离线契约、现场接口快照、文件所有权和集成收据；[接口](../../interfaces/CONTRACT.md) | 当前运动仲裁、统一车载启动、控制闭环与停止链的实际接入验收，不能视为已实现完整驾驶系统 |
| B 数据 | 两路原始记录、独立身份/时钟、事件、导出/质检、只订阅 ROS 入口；[说明](../../data_tools/README.md) | 真实双路记录入口未验收；尚无可共享的正式原始图像会话；没有通用 IMU/sonar 记录或断电恢复 |
| C 感知 | 黑线白路像素路径候选、无效/歧义拒绝、图像回放/叠加；[说明](../../perception/README.md) | 真实画面验证、目标识别与高级任务事件；窄深阴影可能误识别，视野不含两侧蓝区时可能大量拒绝 |
| D 任务 | 两圈/任务证据顺序、停稳计时、等杆、倒库条件及假事件回放；[说明](../../mission/README.md) | 公共输出始终是零速停车请求；实际事件生成、轨迹规划、绕桶/环岛/倒库控制尚待开发 |

离线阶段已有 90 项测试与 B 记录→导出→C 回放→契约校验的 6 帧合成贯通证据，见[阶段集成收据](../OFFLINE_STAGE_RECEIPT.md)。这些没有证明真实双路采集性能、道路准确率或车辆完赛。`road.valid=true` 只是图像像素路径成立，不是车辆净空或运动许可。

部分早期 HANDOFF 写着 `uncommitted` 或原开发电脑路径，描述的是交付当时状态。B/C/D 已归档为仓库代码，当前版本以 `git rev-parse HEAD` 为准；克隆不包含被忽略的现场快照、原图、模型和旧测试输出。不要依赖历史产物目录才能开始开发。

## 克隆后先跑一条离线链路

无需先学习工作树。每人用自己的克隆，按总控分配的模块工作；共用目录时先约定文件所有权，不能同时改同一文件。公共接口由 A 维护，提出变更后统一版本；原始数据只读，共享硬件仍需统一安排。

完成首页的依赖安装后，在本机仓库根目录执行以下 **PowerShell** 命令：

```powershell
python -c "import sys, numpy, PIL; print(sys.executable); print(numpy.__version__, PIL.__version__)"
$batch = 'competition/tests/offline/outputs/team_' + [guid]::NewGuid().ToString('N')
python -B competition/tests/offline/verify_data_perception.py --output $batch
```

第一条核实正在使用的解释器和依赖，缺依赖时先修环境。第二条是现成的纯合成贯通入口，预期 6 帧、12 条公共记录、4 条有效道路、2 条无效道路、动作示范样本 0。查看新目录中的导出、叠加图和 `ROOT_ACCEPTANCE.json`；失败停在该链路排查，不连接小车补测。输出必须全新，不删旧批次重跑。

Linux 同样从仓库根目录运行，以已核实的 `python3` 为解释器，为 `--output` 指定未使用的新目录。单模块测试命令在首页；不要在仓库根盲跑所有历史测试或批量导入 `reference/`。原厂 `data_collect.py` 会清空固定训练目录，禁止直接运行。

## 从现在推进到两圈

| 阶段 | 主要动作 | 进入下一阶段需要的证据 |
|---|---|---|
| 首段手柄视觉采集 | 甲驾驶直道和普通弯，乙记录两相机，停车后丙回放 | 双路原图、正常关闭、质检及叠加结果；见[新版执行方案](NEXT_SESSION_PLAN.md) |
| 正式场景数据 | 先分段覆盖直道/弯道/分叉、桶、环岛、人行道/横杆和车库 | 逐场景可用与失败清单；停止/倒车/纠正等原始内容完整 |
| 感知和任务补齐 | C 用真实帧查误识别，D/A 补实际任务证据与控制接口 | 可回查输入/输出、未知与失效处理；不是只补几个布尔值假装经过路段 |
| 基础运动与停止 | 恢复现场窗口后由甲/A 核实三轴反馈、符号、延迟和停车 | 外部测量与命令/反馈对应、停止能力、唯一实际速度来源 |
| 单项运动 | 分别验收完整弯、绕桶、环岛、横道等杆、倒库 | 明确起止端点、轮胎视角与任务证据；关键项建议连续 3 次通过 |
| 连续路段→一圈 | 验收衔接和计圈，第一圈不入库 | 不重启、不搬车、不依赖人工逐段指挥 |
| 两圈含倒库 | 两种落杆圈次、最后真实倒车入库和停车 | 同一程序连续、无人工干预、无漏项；建议至少连续 3 次并复验合法摆位/光照变化 |

上述次数是团队内部目标，不是官方次数或统计可靠性保证。每次先写目标、版本、主要改变、固定条件、通过条件和退出条件。连续两次同类失败就先做离线复核，不反复追加现场试跑。

## 是否用 YOLO，以及最后两周怎样收敛

先从真实图像判断道路、锥桶、人行道、横杆和车库的实际识别缺口。在同一批开发会话比较简单视觉方法和已有模型；如果所需类别缺失或现有方法持续误检/漏检，再由丙给出类别、标注规范、数据量、算力与部署验证方案。训练需要另行安排，不是拍完录像的自动下一步。检测框不会自动成为路线、圈数或停车决定。

| 内部时间点 | 交付目标与取舍 |
|---|---|
| 10/14—18 | 首段手柄视觉采集与当场回放、针对性补采、关键规则核对；并行推进核心构建和控制接入 |
| 10/19—20 | 确定主方案和数据接口；数据不可用就先修采集，不同时启动多套训练 |
| 10/21—24 | 补齐事件与控制，逐项及连续路段验收；尚不能一圈就停止提速和算法大换代 |
| 10/25—27 | 两圈加倒库、两种落杆情况；未达标如实保存失败证据 |
| 10/28 | 冻结功能、版本、配置、启动/停止/回退说明 |
| 10/29—31 | 只修阻断问题并回归，演练冷启动/恢复，整理数据/视频/报告与最终交付 |

设备或现场条件延迟时压缩并行研究与提速，不跳过必要验收。整车最后应能照一张操作卡运行，不能依赖几个 AI 聊天同时在线。官方规则和报名材料由乙核对，厂商代码、团队修改、数据/模型来源与 AI 辅助情况如实记录。
